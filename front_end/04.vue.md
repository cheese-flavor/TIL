### watchers ###
```
watch = 하나 이상의 반응형 데이터를 감시하고, 감시하는 데이터가 변경되면 콜백 함수 호출

watch(source, (newValue, oldValue)) => {
  // do something
}
- 첫번재 인자: 감시하는 대상 / 두번째 인자: 변화값 / 세번째 인자: 기존값

  watch(count, (newValue, oldValue) => {
    console.log(`newValue: ${newValue}, oldValue: ${oldValue}`)
  })


    Computed   /    Watchers (감시!!!!)
-> 계산값 반환 vs 감시 및 작업 수행
-> 중복계산 방지 vs 변화에 따른 특정 작업 수행
-> 연산길이,필터링 vs DOM변경, 비동기, 외부api감시

*종속되어있다보니 값변경을 함부로 해서는 안됨 / 감시하는 주체를 직접 바꾸면 무한반복

```

### state Management ###
```
컴포넌트 구조의 단순화
- 상태: 앱 구동에 필요한 기본 데이터
- 뷰: 상태를 선언적으로 매핑하여 시각화
- 기능: 뷰에서 사용자 입력에 대해 반응적으로 상태변경가능하게 정의된 동작
-> 단방향 데이터 흐름의 간단한 표현

여러 컴포넌트가 이러한 상황으로 관리하면 단순성이 무너짐
- 여러뷰가 동일한 상태에 종속: 계층구조가 복잡해지면
- 여러뷰가 동일한 상태를 변경: 패턴이 깨지기 쉬움


해결책
1. 각 컴포넌트의 공유상태를 추출하여 전역에서 참조할 수 있는 저장소 관리
2. pinia(피냐)를 활용하자 
```

### Routing ###
```
네트워크에서 경로를 선택하는 프로세스

- SSR에서 routing은 서버측에서 수행
- CSR에서 routing은 클라측에서 수행
- 클라측은 js가 새 데이터를 동적으로 가져와 전체 페이지를 다시 로드하지 않음

spa에서 routing이 없다면
- 유저가 url을 통해 페이지의 변화를 감지할수 없음
- 페이지가 무엇을 렌더링 중인지에 대한 상태를 알 수 없음
  - 새로고침하면 처음 페이지가 됨 / 링크 공유도 첫페이지만
- 브라우저의 뒤로가기 기능을 사용할 수 없음

-> 페이지는 1개이지만, 주소에 따라 여러 컴포넌트를 새로 렌더링
   마치 여러페이지를 사용하는것처럼 보여야함
```
